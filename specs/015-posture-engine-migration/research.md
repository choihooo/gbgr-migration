# Research: 자세 측정 엔진 분리 이관

## 결정 1: 화면 표시 모드와 백그라운드 측정 모드를 분리한 이원화 구조를 채택한다

- 결정: 사용자가 앱을 보고 있을 때는 React가 카메라 미리보기와 오버레이를 렌더링하고, 자세 추론 결과는 별도 측정 엔진에서 공급받는다. 앱이 최소화되거나 숨김 상태가 되면 화면 렌더링은 멈추고 측정 엔진만 백그라운드에서 계속 동작한다.
- 근거: `docs/POSTURE_ENGINE_ARCHITECTURE.md`가 요구하는 핵심 조건이 실시간 UI 유지와 최소화 상태 측정 지속을 동시에 충족하는 것이며, 이 두 목적은 동일한 실행 루프보다 모드 분리가 더 안정적이다.
- 고려한 대안:
  - 렌더러 단일 루프 유지: 최소화 상태에서 렌더러 스로틀링 영향을 크게 받아 제외
  - 항상 백그라운드 엔진이 카메라를 직접 점유: 메인 화면/보정 화면의 실시간 미리보기와 UI 일체감을 깨뜨려 제외

## 결정 2: 자세 추론과 분류는 Python sidecar에서 수행하고, React는 더 이상 웹 MediaPipe 추론을 담당하지 않는다

- 결정: 포그라운드와 백그라운드 모두에서 자세 추론과 자세 계산의 실행 주체는 Python sidecar로 통일한다. React는 카메라 미리보기와 오버레이 소비를 담당하고, 포그라운드 모드에서는 샘플링한 프레임을 Rust 브리지로 전달한다.
- 근거: 헌법은 Python 전환을 별도 기능 스펙으로 분리하라고 요구하며, 중간 단계에서 웹 MediaPipe와 Python MediaPipe를 혼합 운영하는 임시 구조를 금지한다. 따라서 이번 기능 범위에서는 추론 책임을 한 번에 sidecar로 이동하는 편이 규칙에 맞다.
- 고려한 대안:
  - 포그라운드만 웹 MediaPipe 유지: 헌법이 금지한 혼합 운영이 되어 제외
  - Rust에서 직접 추론 수행: 현재 저장소와 설계 메모의 방향이 Python MediaPipe sidecar 기준이므로 제외

## 결정 3: 카메라 소유권은 “한 시점 한 주체” 원칙으로 전환한다

- 결정: 포그라운드 모드에서는 React의 `react-webcam`이 카메라를 점유하고, 백그라운드 모드에서는 Python sidecar가 카메라를 점유한다. 전환 시에는 기존 소유자가 장치를 완전히 해제한 뒤 다음 소유자가 점유한다.
- 근거: 설계 메모와 스펙 모두 카메라 충돌 방지를 핵심 제약으로 두고 있으며, 실제 레거시/마이그레이션 코드에서도 `WebcamPanel`과 `WebcamView`가 카메라 표시를 전제로 하고 있다.
- 고려한 대안:
  - React와 Python이 동시에 카메라를 여는 공유 전략: 장치 충돌과 초기화 실패 가능성이 커 제외
  - 모든 모드에서 Python이 점유하고 React는 프레임만 표시: 현재 UI 구조와 개발 난이도를 불필요하게 높여 제외

## 결정 4: React와 Rust 사이의 인터페이스는 Tauri command/event 계약으로 고정한다

- 결정: 프론트엔드는 자세 엔진 제어와 상태 조회를 Tauri command로 요청하고, 자세 결과/엔진 상태/경고는 Tauri event로 수신한다.
- 근거: 헌법 3번이 Electron IPC 모방 대신 Tauri command 패턴을 요구하고 있고, 현재 `migration/src-tauri/src/lib.rs`도 Tauri command 등록 구조를 사용한다.
- 고려한 대안:
  - 프론트엔드가 시스템 API를 직접 호출: 헌법 위반이라 제외
  - 폴링 전용 구조: 모드 전환과 경고 상태를 실시간으로 전달하기 어려워 제외

## 결정 5: 최신 자세 상태는 Rust가 캐시하고, 화면 복귀 직후 즉시 전달한다

- 결정: Rust 백엔드는 최신 측정 결과와 엔진 상태를 메모리에 캐시하고, 프론트엔드 복귀 시 `get_latest_posture_state` 계열 조회로 즉시 전달한다.
- 근거: 설계 메모의 “복귀 직후 마지막 결과 먼저 렌더링” 요구를 만족하려면 UI 외부의 신뢰 가능한 상태 보관자가 필요하다. Rust는 프론트엔드 생명주기와 분리되어 있어 이 역할에 적합하다.
- 고려한 대안:
  - 프론트엔드 상태만 유지: 최소화/복귀나 창 재활성화 구간에서 신뢰성이 떨어져 제외
  - sidecar에만 상태 보관: 프론트엔드 복귀 시 조회 경로가 늘고 Rust 알림 판단과 중복되어 제외

## 결정 6: 결과 계약은 “렌더링용 결과”와 “운영 상태”를 분리한다

- 결정: 자세 결과 이벤트는 랜드마크, 자세 클래스, 점수, 시각 같은 렌더링 중심 필드를 담고, 엔진 상태 이벤트는 모드, 상태, 소유권, 마지막 오류를 담는다.
- 근거: UI는 오버레이와 배지 갱신에 필요한 정보와, 엔진 준비/전환/오류를 사용자에게 드러내기 위한 정보를 분리해서 소비한다. 두 종류를 나눠야 화면 로직이 단순해진다.
- 고려한 대안:
  - 모든 정보를 하나의 대형 이벤트에 합치기: 이벤트 의미가 모호해지고 상태 변경만으로도 큰 페이로드가 반복되어 제외
  - 결과 이벤트만 두고 상태는 UI가 추론: 오류 복구와 모드 전환 시 오판 가능성이 커 제외

## 결정 7: 보정 화면과 메인 화면은 동일한 결과 계약을 공유하되, 소비 방식만 다르게 둔다

- 결정: 보정 화면과 메인 화면은 동일한 자세 결과 계약을 구독하되, 보정 화면은 품질 판단/카운트다운에 집중하고 메인 화면은 실시간 오버레이와 상태 피드백에 집중한다.
- 근거: 스펙은 보정과 메인이 같은 자세 의미를 유지해야 한다고 요구한다. 소비 목적이 달라도 결과 원천은 같아야 회귀 검증이 가능하다.
- 고려한 대안:
  - 화면별로 다른 결과 계약 사용: 같은 자세라도 화면마다 해석이 달라질 수 있어 제외
  - 보정 화면 전용 추론 분기: 규칙 유지와 검증 비용 측면에서 불리해 제외

## 결정 8: Python sidecar 런타임 기준은 Python 3.11로 둔다

- 결정: 계획 단계의 sidecar 기준 런타임은 Python 3.11로 둔다.
- 근거: Spec template 예시 수준이 아니라 실제 구현 계획에서 버전 기준이 필요하며, Python 3.11은 현재 범용 패키지 호환성과 성능/지원 균형이 좋아 sidecar 표준 버전으로 삼기 적절하다.
- 고려한 대안:
  - 버전 미정으로 남기기: 이후 번들 전략, 의존성 잠금, 검증 절차 작성이 어려워 제외
  - Python 3.12 이상: 일부 네이티브 의존성과 번들링 안정성을 선검증 없이 가정하게 되어 제외
