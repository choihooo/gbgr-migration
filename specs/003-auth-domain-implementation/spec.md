## User Scenarios & Testing *(mandatory)*

### User Story 1 - 기존 계정으로 안전하게 로그인한다 (Priority: P1)

기존 사용자는 앱을 다시 실행했을 때 즉시 로그인 상태를 복구하거나, 필요 시 로그인 화면에서 이메일과 비밀번호를 입력해 서비스에 진입할 수 있어야 한다. 인증이 완료되면 보호된 화면으로 이동하고, 인증이 없거나 만료된 경우에는 공개 인증 흐름으로 되돌아가야 한다.

**Why this priority**: 로그인과 세션 복구는 앱 진입의 시작점이며, 이 흐름이 완성되어야 보호 라우트와 이후 사용자 경험 전체가 정상 동작한다.

**Independent Test**: 저장된 인증 정보가 없는 상태와 있는 상태 각각에서 앱을 실행해, 로그인 성공 시 보호 화면으로 이동하고 실패 또는 만료 시 로그인 화면으로 복귀하는지 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 유효한 인증 정보를 저장하지 않은 상태로 앱을 실행했을 때, **When** 보호된 화면에 접근하려고 하면, **Then** 로그인 화면으로 이동하고 원래 목적지 정보는 유지되어야 한다.
2. **Given** 사용자가 유효한 이메일과 비밀번호를 입력했을 때, **When** 로그인을 완료하면, **Then** 인증 상태가 저장되고 사용자는 원래 요청한 보호 화면으로 우선 복귀하며, 해당 정보가 없을 때만 보호된 기본 진입 화면으로 이동해야 한다.
3. **Given** 사용자가 이전에 저장된 유효한 인증 정보를 가진 상태로 앱을 다시 실행했을 때, **When** 앱 초기화가 완료되면, **Then** 로그인 화면을 다시 거치지 않고 보호된 화면으로 복구되어야 한다.
4. **Given** 저장된 인증 정보가 만료되었거나 더 이상 유효하지 않을 때, **When** 앱이 인증 복구를 시도하면, **Then** 저장된 인증 정보는 정리되고 사용자는 로그인 화면으로 안내되어야 한다.
5. **Given** 사용자가 아직 이메일 인증을 완료하지 않은 계정으로 로그인을 시도했을 때, **When** 로그인 요청 결과가 미인증 상태로 판별되면, **Then** 사용자는 일반 실패로 머무르지 않고 이메일 인증 대기 또는 재발송 흐름으로 안내되어야 한다.

---

### User Story 2 - 신규 사용자가 가입 후 이메일 인증을 완료한다 (Priority: P2)

신규 사용자는 회원가입 화면에서 필요한 정보를 입력하고 가입을 요청한 뒤, 이메일 인증 안내 화면과 인증 콜백 흐름을 통해 계정을 활성화할 수 있어야 한다. 인증이 끝나면 사용자는 로그인으로 자연스럽게 이어질 수 있어야 한다.

**Why this priority**: 신규 사용자 유입의 핵심 흐름이며, 로그인만 가능한 상태로는 제품 확장이 제한된다.

**Independent Test**: 가입 정보를 제출하고 인증 메일 안내 화면, 이메일 인증 콜백 화면, 이후 로그인 유도까지의 흐름을 별도로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 회원가입에 필요한 정보를 모두 유효하게 입력했을 때, **When** 가입을 완료하면, **Then** 계정 생성 요청이 처리되고 이메일 인증 안내 화면으로 이동해야 한다.
2. **Given** 사용자가 회원가입 화면에서 필수 값이 누락되었거나 형식이 올바르지 않은 값을 입력했을 때, **When** 가입을 시도하면, **Then** 해당 필드별 안내가 표시되고 가입 요청은 진행되지 않아야 한다.
3. **Given** 사용자가 이메일 인증 안내를 받은 상태일 때, **When** 메일의 인증 링크를 통해 인증을 완료하면, **Then** 인증 완료 콜백 화면이 표시되고 로그인 행동으로 이어질 수 있어야 한다.

---

### User Story 3 - 인증 메일을 다시 받고 상태를 이어서 진행한다 (Priority: P3)

이메일을 받지 못했거나 앱을 중간에 종료한 사용자는 마지막으로 가입 중이던 이메일 정보를 바탕으로 인증 메일을 다시 요청하고, 인증 대기 상태를 이어서 확인할 수 있어야 한다.

**Why this priority**: 가입 중 이탈한 사용자를 회복시키는 흐름이며, 이메일 전달 지연이나 앱 재실행 상황에서 가입 실패 경험을 줄인다.

**Independent Test**: 가입 직후와 앱 재실행 후 각각에서 인증 메일 재발송과 이메일 정보 복원 여부를 별도 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 이메일 인증 대기 화면에 있는 상태일 때, **When** 인증 메일 재발송을 요청하면, **Then** 동일한 이메일 대상으로 재발송이 처리되고 사용자에게 결과가 안내되어야 한다.
2. **Given** 사용자가 인증 메일 재발송 전용 화면에 진입했을 때, **When** 이전 가입 흐름에서 사용한 이메일 정보가 남아 있다면, **Then** 사용자는 해당 이메일을 확인한 뒤 재발송을 요청할 수 있어야 한다.
3. **Given** 재발송 대상 이메일 정보가 존재하지 않을 때, **When** 사용자가 재발송 화면에 진입하면, **Then** 이메일 정보 없음 상태가 명확히 안내되고 사용자는 가입 또는 로그인 흐름으로 복귀할 수 있어야 한다.

### Edge Cases

- 사용자가 보호된 화면으로 직접 진입했지만 인증 복구가 아직 끝나지 않은 경우, 앱은 보호 화면을 노출하지 않고 인증 확인이 끝날 때까지 중간 상태를 유지해야 한다.
- 사용자가 로그인 또는 회원가입 중 네트워크 오류를 만나면, 입력 중인 값은 유지되고 재시도 가능한 오류 안내가 제공되어야 한다.
- 사용자가 이미 가입된 이메일로 다시 회원가입을 시도하면, 중복 상태가 명확히 표시되고 다음 행동을 선택할 수 있어야 한다.
- 사용자가 만료되었거나 잘못된 이메일 인증 링크를 열면, 성공 상태로 오인되지 않도록 실패 안내와 다음 이동 경로가 제공되어야 한다.
- 사용자가 이메일 인증을 완료하지 않은 계정으로 로그인을 시도하면, 단순 오류로 끝나지 않고 인증 대기 또는 재발송 경로로 이동할 수 있어야 한다.
- 사용자가 로그아웃되었거나 인증이 해제된 뒤 뒤로 가기 또는 저장된 보호 경로로 재진입하면, 보호 콘텐츠 대신 공개 인증 흐름으로 안내되어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 인증이 없는 사용자가 공개 인증 화면에서 로그인, 회원가입, 이메일 인증 대기, 인증 메일 재발송, 이메일 인증 콜백 흐름을 순차적으로 수행할 수 있게 해야 한다.
- **FR-002**: 시스템은 로그인 시 사용자가 입력한 이메일과 비밀번호를 검증하고, 인증에 성공한 경우 보호된 앱 영역 접근 권한을 부여해야 한다.
- **FR-003**: 시스템은 회원가입 시 이메일, 비밀번호, 비밀번호 확인, 이름 입력값의 유효성을 검증하고, 오류가 있는 경우 필드 단위로 안내해야 한다.
- **FR-004**: 시스템은 회원가입 과정에서 이메일 중복 여부를 확인할 수 있게 해야 하며, 중복 확인이 완료되지 않으면 가입 완료를 진행시키지 않아야 한다.
- **FR-005**: 시스템은 회원가입이 성공하면 사용자를 이메일 인증 대기 상태로 전환하고, 인증 메일이 발송되었음을 현재 화면 문구 체계에 맞춰 안내해야 한다.
- **FR-006**: 시스템은 이메일 인증 대기 상태의 사용자가 인증 메일 재발송을 요청할 수 있게 해야 하며, 성공 또는 실패 결과를 현재 화면 흐름 안에서 확인할 수 있게 해야 한다.
- **FR-007**: 시스템은 이메일 인증 링크를 통해 유입된 사용자의 인증 완료 여부를 판별하고, 성공 시 인증 완료 안내를 제공하며 이후 로그인으로 이어지게 해야 한다.
- **FR-008**: 시스템은 잘못되었거나 만료된 인증 링크를 성공으로 처리해서는 안 되며, 사용자가 다시 시도할 수 있는 다음 행동을 안내해야 한다.
- **FR-008-1**: 시스템은 이메일 인증이 완료되지 않은 계정의 로그인 시도를 일반 인증 실패와 동일하게 처리해서는 안 되며, 사용자를 이메일 인증 대기 또는 인증 메일 재발송 흐름으로 안내해야 한다.
- **FR-009**: 시스템은 인증 성공 시 세션 식별 정보와 사용자 식별 정보를 앱 재실행 후에도 복구 가능한 형태로 저장해야 한다.
- **FR-010**: 시스템은 앱 시작 시 저장된 인증 정보를 복구하고, 유효성 확인이 끝날 때까지 인증 상태를 미확정 상태로 관리해야 한다.
- **FR-011**: 시스템은 저장된 인증 정보가 유효한 경우 사용자를 직전에 요청한 보호 경로로 우선 복귀시켜야 하며, 복귀할 보호 경로 정보가 없을 때만 보호된 기본 진입점으로 이동시켜야 한다.
- **FR-012**: 시스템은 저장된 인증 정보가 유효하지 않거나 복구에 실패한 경우 저장된 인증 정보를 정리하고 공개 인증 화면으로 전환해야 한다.
- **FR-013**: 시스템은 보호 라우트 접근 시 인증 여부, 인증 복구 진행 상태, 인증 실패 상태를 구분해 처리해야 하며, 인증이 확정되기 전까지 보호 화면 내용을 노출해서는 안 된다.
- **FR-014**: 시스템은 로그인 이후 접근해야 하는 페이지와 공개 상태에서만 접근해야 하는 페이지를 구분해 잘못된 진입을 자동으로 교정해야 한다.
- **FR-015**: 시스템은 인증과 관련된 사용자 인터페이스의 시각적 스타일, 문구 체계, 화면 배치를 레거시와 동일한 수준으로 유지해야 한다.
- **FR-016**: 시스템은 인증 화면 조합을 담당하는 페이지 계층을 얇게 유지하고, 사용자 액션, 상태 전이, 사용자 정보 관리는 화면 표현 책임과 분리된 구조로 관리되어야 한다.
- **FR-017**: 시스템은 현재 존재하는 다국어 리소스를 기반으로 인증 성공, 실패, 대기, 복구 상태의 사용자 메시지를 일관되게 제공해야 한다.
- **FR-018**: 시스템은 가입 또는 인증 대기 중 사용자가 입력하거나 확인한 이메일 정보를 이후 인증 대기 화면과 재발송 화면에서 이어서 사용할 수 있게 해야 한다.

### Key Entities *(include if feature involves data)*

- **인증 세션**: 사용자의 로그인 상태를 나타내는 정보 묶음이다. 인증 여부, 복구 진행 여부, 만료 또는 무효 상태, 마지막 보호 경로 정보를 포함한다.
- **가입 초안 사용자**: 회원가입 또는 이메일 인증 대기 흐름에 있는 사용자를 나타낸다. 이메일, 이름, 가입 진행 상태, 이메일 중복 확인 완료 여부를 포함한다.
- **인증된 사용자**: 보호 영역 접근 권한이 있는 사용자를 나타낸다. 사용자 식별 정보와 앱 내에서 필요한 최소 프로필 정보를 포함한다.
- **이메일 인증 요청**: 가입 직후 또는 재발송 시점의 인증 메일 발송 상태를 나타낸다. 대상 이메일, 마지막 발송 결과, 재시도 가능 여부를 포함한다.
- **보호 경로 의도**: 인증이 없는 사용자가 진입하려던 보호 화면 목적지를 나타낸다. 인증 완료 후 우선 복귀 경로를 결정하는 기준으로 사용된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 기존 사용자의 95% 이상이 저장된 인증 정보가 유효한 경우 앱 재실행 후 3초 이내에 다시 로그인 화면을 거치지 않고 보호 화면에 진입한다.
- **SC-002**: 유효한 가입 정보를 가진 신규 사용자의 90% 이상이 회원가입 시작부터 이메일 인증 대기 화면 진입까지 2분 이내에 완료할 수 있다.
- **SC-003**: 인증이 없는 사용자의 보호 화면 직접 진입 시도는 100% 공개 인증 흐름으로 전환되고, 보호 화면 콘텐츠가 선노출되지 않는다.
- **SC-004**: 인증 메일 재발송 요청의 95% 이상이 사용자가 동일 세션 안에서 결과 안내를 확인할 수 있는 형태로 처리된다.
- **SC-005**: 로그인, 회원가입, 이메일 인증, 재발송 흐름에서 사용자가 마주치는 주요 실패 상황의 100%에 대해 다음 행동이 명확한 안내가 제공된다.

## Assumptions

- 기존 서비스의 인증 정책과 계정 체계는 유지되며, 이번 범위는 migration 앱에서 해당 정책을 정식으로 연결하는 데 집중한다.
- 비밀번호 찾기나 소셜 로그인 같은 추가 인증 방식은 이번 범위에 포함하지 않는다.
- 현재 migration 앱에 존재하는 인증 화면 구성과 i18n 문구는 그대로 활용하며, 시각적 스타일 변경 없이 상태 연결만 보강한다.
- 앱은 네트워크 연결이 가능한 환경에서 동작하며, 네트워크 실패 시에는 사용자 입력을 보존한 채 재시도 가능한 흐름을 제공한다.
- 보호 라우트의 기본 진입점은 현재 앱에서 이미 정의된 보호 영역 구조를 따른다.
