# Research: 인증 도메인 정식 구현

## 결정 1. 인증 API 계약은 레거시 엔드포인트와 에러 코드를 유지한다

- Decision: `migration`은 레거시가 사용 중인 `/auth/login`, `/auth/sign-up`, `/auth/check-email`, `/auth/verify-email`, `/auth/resend-verification-email`, `/auth/refresh`, `/users/me` 계약과 `AUTH-101`, `AUTH-102` 토큰 에러 의미를 그대로 따른다.
- Rationale: 레거시 `src/renderer/src/entities/user/api/*`와 `src/renderer/src/shared/api/instance.ts`가 이미 검증된 계약을 사용하고 있어, 이 계약을 유지하는 편이 마이그레이션 정합성과 백엔드 재사용 측면에서 가장 안전하다.
- Alternatives considered:
  - 새 인증 엔드포인트를 정의한다: 백엔드 변경과 동시 조정이 필요해 마이그레이션 범위를 불필요하게 키운다.
  - 로그인 응답만 믿고 `/users/me`를 생략한다: 사용자명, `userId`, 후속 온보딩 분기 기준을 일관되게 복구하기 어렵다.

## 결정 2. 인증 복구는 라우터 진입 전 세션 하이드레이션으로 처리한다

- Decision: 보호 라우트의 판별 기준은 단순 `localStorage` 조회가 아니라, 앱 초기화 시 한 번 수행하는 인증 세션 하이드레이션 결과를 기준으로 삼는다.
- Rationale: 현재 `migration/src/shared/config/router.tsx`의 loader는 `accessToken` 존재 여부만 확인하므로, 복구 중간 상태를 표현할 수 없고 보호 화면 선노출 위험도 있다. 앱 초기화 단계에서 세션을 `checking/authenticated/unauthenticated`로 확정하면 공개/보호 라우트를 안정적으로 제어할 수 있다.
- Alternatives considered:
  - 현 loader 방식을 유지한다: refresh token, 사용자 복구, 만료 처리, 원래 경로 복귀를 모두 표현하기 어렵다.
  - 각 페이지에서 개별 `useEffect`로 인증을 확인한다: 페이지가 두꺼워지고 중복 분기가 늘어나며 헌법의 구조 분리 원칙과 맞지 않는다.

## 결정 3. 인증 저장소는 “세션 키”와 “보조 UI 키”를 분리한다

- Decision: `accessToken`, `refreshToken`, `userId`, `userName`, 보호 경로, 인증 복구 플래그는 인증 세션 저장소에서 관리하고, `savedEmail`, 가입 중 이메일, 앱 언어 등 보조 UI 값은 별도 키로 유지한다.
- Rationale: 레거시에는 `localStorage.clear()`가 포함된 흐름이 있지만, `migration`은 i18n 언어 저장과 이후 다른 도메인 상태가 이미 존재한다. 인증 키만 선택적으로 정리해야 부수 효과 없이 점진적 마이그레이션이 가능하다.
- Alternatives considered:
  - 모든 키를 그대로 전역 `localStorage`에 흩어 저장한다: 키 충돌과 정리 누락이 생기기 쉽다.
  - 로그아웃/인증 완료 시 전체 `localStorage.clear()`를 사용한다: 언어 설정과 타 도메인 데이터를 의도치 않게 제거할 수 있다.

## 결정 4. 미인증 로그인은 일반 실패가 아니라 인증 대기 복구 흐름으로 보낸다

- Decision: 로그인 응답이 “이메일 미인증” 상태를 가리키면, 사용자를 일반 로그인 실패에 머무르게 하지 않고 이메일 인증 대기 또는 재발송 화면으로 보낸다.
- Rationale: 이는 clarify 단계에서 확정된 요구사항이며, 신규 사용자 회복 경로를 제공한다. 단순 에러 처리보다 사용자 성공률과 테스트 가능성이 높다.
- Alternatives considered:
  - 일반 로그인 실패로만 보여준다: 사용자가 다음 행동을 알기 어렵다.
  - 제한적 로그인 허용 후 보호 기능을 막는다: 인증 모델이 복잡해지고 스펙 범위를 넘어선다.

## 결정 5. 로그인 후 복귀는 원래 요청한 보호 경로를 우선한다

- Decision: 공개 상태에서 보호 라우트 접근 시 원래 목적지를 저장하고, 로그인 또는 세션 복구 성공 후 해당 경로로 우선 복귀한다. 목적지가 없을 때만 보호 기본 진입점으로 이동한다.
- Rationale: clarify 단계에서 확정된 요구사항이며, 보호 라우트 테스트와 사용자 경험 모두 가장 자연스럽다.
- Alternatives considered:
  - 항상 `/main`으로 보낸다: 보호 라우트 직접 진입 시 기대 행동과 어긋난다.
  - 사용자가 직접 다음 이동을 선택하게 한다: 인증 도메인 범위 밖 UI를 추가로 설계해야 한다.

## 결정 6. 이메일 인증 콜백은 “토큰 1회 처리 + 결과 화면 유지” 방식으로 구현한다

- Decision: 콜백 페이지는 URL의 `token`을 한 번만 처리하고, 성공/실패 결과를 화면 상태로 유지한다. 성공 시 자동 로그인은 하지 않고 로그인 행동으로 이어지게 한다.
- Rationale: 레거시 콜백 페이지와 현재 `migration`의 i18n 문구가 모두 “앱으로 돌아가 로그인” 흐름을 전제로 한다. 자동 로그인을 추가하면 레거시 사용자 경험과 달라진다.
- Alternatives considered:
  - 인증 성공 즉시 자동 로그인한다: 레거시 플로우와 달라지고 세션 초기화 규칙이 복잡해진다.
  - 콜백에서 결과 처리 없이 정적 화면만 보여준다: 잘못된 링크와 성공 링크를 구분하지 못해 스펙 요구를 충족하지 못한다.

## 결정 7. 테스트는 순수 로직 단위 테스트 + 수동 회귀 시나리오 조합으로 시작한다

- Decision: 새 인증 스토어, 토큰 정리 유틸, 라우트 분기 함수처럼 순수한 로직에는 단위 테스트를 추가하고, 실제 로그인/가입/인증/재발송/세션 복구 흐름은 수동 회귀 시나리오로 검증한다.
- Rationale: 현재 `migration`에는 테스트 러너가 아직 없지만, 인증 상태 전이는 회귀 위험이 높다. 순수 함수 테스트를 먼저 도입하면 비용 대비 효과가 좋고, UI 동일성은 수동 시나리오로 확인하는 편이 프로젝트 원칙과 맞다.
- Alternatives considered:
  - 수동 테스트만 사용한다: 세션 만료/복구 같은 분기 회귀를 반복 검증하기 어렵다.
  - 처음부터 전면 E2E를 도입한다: 현재 단계 대비 설정 비용이 크고 인증 도메인 범위를 넘어간다.
