# GBGR Migration Constitution

## 전문

이 프로젝트는 GBGR(거부기린) Electron 웹뷰 앱을
Tauri + React Native UI 앱으로 마이그레이션하는 작업이다.

`src/`는 레거시 Electron 코드이며,
`migration/`에 Tauri 기반 새 앱을 구축한다.
마이그레이션은 레거시의 기능과 UI를 충실히 재현하되,
아키텍처는 Tauri 패턴에 맞게 재설계한다.

이 헌법은 PR, 리뷰, CI에서 즉시 집행되는 기준이다.
모든 변경은 아래 원칙을 만족해야 하며,
예외는 승인권자, 기록 방식, 만료일이 명시된 경우에만 유효하다.

## Core Principles

### 1. 레거시 존중

**Why**: `src/`의 Electron 코드는 마이그레이션의 원천이다.
레거시를 임의로 수정하면 원본 기능이 훼손되어
마이그레이션 결과물의 정합성을 검증할 수 없다.

**Rules**:

- `src/`의 레거시 코드는 읽기 전용으로 취급한다.
  수정이 필요하면 먼저 물어보고 승인 후 반영한다.
- 레거시의 비즈니스 로직, 임계값, 분류 알고리즘,
  세션 관리 정책은 동일하게 포팅한다.
  마이그레이션 중에 기능을 임의로 추가, 제거, 변경하지 않는다.
- 포팅된 코드는 레거시와의 정합성을 검증할 수 있어야 한다.

**Check**:

- `src/` 내 파일 변경이 포함된 PR은 변경 사유와 승인 근거를
  본문에 포함해야 한다.
- 레거시 로직 포팅 시 원본 파일 경로와 라인을 PR에 명시한다.

### 2. UI 충실도 보존

**Why**: 마이그레이션의 핵심 제약은 UI 스타일 변경 금지다.
사용자가 마이그레이션 전후로 동일한 경험을 가져야 한다.

**Rules**:

- 기존 UI의 색상, 간격, 타이포그래피, 레이아웃, 애니메이션을
  그대로 유지한다. 개인 취향이나 "개선"을 이유로
  시각적 요소를 변경하지 않는다.
- 디자인 토큰(색상, 폰트, 간격)은 레거시 CSS/Tailwind 값에서
  추출하여 Tauri 앱의 디자인 시스템으로 이관한다.
- 새로운 UI 패턴이나 컴포넌트 구조는 기능 동등성을
  보장하는 범위에서만 도입한다.

**Check**:

- UI 변경이 포함된 PR은 before/after 스크린샷 또는
  레거시 화면 캡처와의 비교를 포함해야 한다.
- 리뷰에서 의도하지 않은 시각적 차이를 확인한다.

### 3. Tauri 아키텍처 준수

**Why**: Electron의 main/preload/renderer 구조에서
Tauri의 Rust backend + webview frontend 구조로 전환한다.
Tauri의 보안 모델과 아키텍처 패턴을 따르지 않으면
마이그레이션의 이점이 사라진다.

**Rules**:

- Tauri 명령어(Custom Commands)는 Rust 측에 정의하고,
  TypeScript에서는 `@tauri-apps/api`를 통해 호출한다.
  Electron의 IPC 패턴을 그대로 모방하지 않는다.
- OS 부작용(알림, 파일 시스템, 업데이트, 분석 전송)은
  Rust 백엔드에서만 수행한다.
  프론트엔드는 Tauri API를 통해 요청만 보낸다.
- 보안: Tauri의 권한 시스템(capabilities)을 사용하여
  최소 권한 원칙을 적용한다.
  프론트엔드가 필요 이상의 시스템 접근 권한을 가지지 않도록 한다.

**Check**:

- 신규 Tauri 명령어는 권한 범위와 입력 검증을
  PR에 명시해야 한다.
- 프론트엔드에서 직접 시스템 API를 호출하는 코드는 반려한다.

### 4. 점진적 마이그레이션

**Why**: 한 번에 전체 앱을 마이그레이션하면
통합 이슈가 폭발적으로 증가하여 롤백이 불가능해진다.
기능 단위로 점진적으로 포팅하여 각 단계의 정합성을 보장한다.

**Rules**:

- 마이그레이션은 기능 단위(인증, 자세 분석, 대시보드,
  알림, 위젯 등)로 진행한다.
- 각 기능 포팅 후 레거시와의 동등성을 검증한다.
  검증 없이 다음 기능으로 넘어가지 않는다.
- 레거시에서 새 앱으로 이관하는 상태 관리 패턴:
  Zustand 클라이언트 상태 → Zustand 유지,
  TanStack Query 서버 상태 → TanStack Query 유지.
  기존 상태 관리 전략의 분리 원칙을 그대로 따른다.
- 포팅 순서는 의존성 그래프를 기준으로 결정한다.
  기반이 되는 모듈(인증, API 클라이언트)을 먼저 이관한다.

**Check**:

- 기능 포팅 PR은 이관 범위, 레거시 원본 위치,
  검증 결과를 포함해야 한다.
- 상태 관리 이관 시 Zustand/Query 책임 분리 원칙을
  준수했는지 확인한다.

### 5. 품질 게이트 강제

**Why**: 마이그레이션 중 품질이 저하되면
최종 산출물의 신뢰성을 보장할 수 없다.
각 단계에서 품질 기준을 통과해야 다음 단계로 진행한다.

**Rules**:

- lint, typecheck, 빌드 중 하나라도 실패하면 merge하지 않는다.
- 포팅된 핵심 로직(PostureClassifier, ScoreProcessor,
  calibration, 세션 관리, 알림 스케줄러)은
  회귀 위험과 검증 비용을 기준으로 필요한 범위에서만
  단위 테스트, E2E 테스트, 또는 수동 검증 시나리오를 추가한다.
- 테스트는 "많을수록 좋다"가 아니라
  회귀를 조기에 잡는 데 실질적으로 도움이 되는 경우에만 추가한다.
  단순 마크업 이관, 정적 문구 변경, 시각 복제처럼
  리스크가 낮은 변경에는 테스트를 강제하지 않는다.
- Tauri 명령어의 입력 검증과 에러 처리는 필수다.
  검증 없는 명령어는 merge하지 않는다.
- 기능 포팅 완료 기준:
  레거시와 동일한 입력에 동일한 출력을 내는지 확인한다.

**Check**:

- CI 필수 체크를 브랜치 보호 규칙으로 연결한다.
- 핵심 로직 포팅 PR에 왜 해당 테스트가 필요한지
  또는 왜 수동 검증만으로 충분한지 근거를 첨부해야 한다.
- 리뷰에서 신규 경고, suppress 주석, 우회 코드를 확인한다.

## Governance

### 개정 규칙

- 헌법 개정은 PR로만 수행한다.
- 원칙 추가, 제거, 의미 재정의는 MINOR 이상 버전을 올린다.
- 규칙의 집행 기준을 바꾸는 후방 비호환 변경은
  MAJOR 버전을 올린다.
- 오탈자, 표현 명확화, 예시 보강은 PATCH 버전을 올린다.
- 개정 PR에는 변경 이유, 영향 범위, 기존 규칙과의 차이,
  필요한 템플릿 동기화 결과를 반드시 포함한다.

### 예외 규칙

- 아키텍처/UI 예외 승인권자:
  Tech Lead 1인 + 해당 영역 Owner 1인.
- 예외 기록 방식:
  PR 본문에 위반 조항, 필요한 이유, 대안 검토,
  완화 조치, 담당자, 만료일을 남긴다.
- 예외 만료일은 승인일 기준 30일 이내로 설정한다.
  만료일이 지난 예외는 자동 무효다.

### 위반 처리

- CI 실패, 규칙 누락, 예외 기록 누락 상태의 PR은
  merge하지 않는다.
- 리뷰어는 위반 원칙 번호를 명시해 반려한다.
- 포팅 후 발견된 정합성 위반은 다음 영업일 내에
  회고 항목으로 등록하고 재발 방지 액션을 남긴다.

### 개발 도구 규칙

- 패키지 관리: 개발 환경에서는 `bun`을 사용하고, 프로덕션(Tauri 런타임)에서는 `node`를 사용한다.
  의존성 추가, 스크립트 실행 등 개발 작업에는 `bun add`, `bun run` 등 bun 명령어를 사용한다.
