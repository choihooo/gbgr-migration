# GBGR 전체 마이그레이션 문서

## 1. 문서 목적

이 문서는 `src/` 레거시 Electron 앱을 `migration/` Tauri + React 앱으로 이전하기 위한 전체 기준 문서다.  
기능별 개별 스펙 문서와 별도로, 아래 내용을 한 번에 정리하는 상위 문서로 사용한다.

- 왜 마이그레이션하는지
- 무엇을 어디까지 옮길지
- 어떤 원칙으로 구조를 개선할지
- 어떤 순서로 이전할지
- 각 단계의 완료 기준이 무엇인지

이 문서는 이후 기능별 스펙, 작업 문서, 구현 우선순위의 기준점으로 사용한다.

---

## 2. 마이그레이션 목표

### 2.1 제품 목표

- 기존 웹뷰 기반 Electron 앱을 Native UI 기반 Tauri 앱으로 전환한다.
- 사용자가 느끼는 핵심 기능과 화면 흐름은 유지한다.
- 기존 서비스 동작을 깨지 않으면서 데스크톱 앱 구조를 장기 유지보수 가능한 형태로 개선한다.

### 2.2 기술 목표

- Electron 의존 로직을 Tauri 플러그인과 Tauri 런타임 구조로 치환한다.
- 레거시 구조를 그대로 복제하지 않고, 유지보수 가능한 도메인 구조로 재정리한다.
- 라우팅, 인증, API, 상태관리, i18n, 윈도우 제어, 알림, 자동 실행, 업데이트 등 데스크톱 기능을 Tauri 기준으로 재구성한다.

### 2.3 품질 목표

- UI 스타일은 변경하지 않는다.
- 사용자 플로우와 주요 경로는 레거시와 동일하게 유지한다.
- 각 단계마다 빌드 가능 상태를 유지한다.

---

## 3. 마이그레이션 원칙

### 3.1 유지 원칙

- 화면 스타일은 레거시와 동일하게 유지한다.
- 주요 사용자 플로우는 레거시와 동일하게 유지한다.
- 기존 API 계약은 가능한 한 그대로 유지한다.
- 라우팅 경로와 주요 상태 키는 불필요하게 변경하지 않는다.

### 3.2 개선 원칙

- UI는 유지하되 구조는 개선한다.
- UI 로직과 비즈니스 로직은 분리하고, 화면은 표현과 조합에 집중하며 도메인 규칙과 상태 변화는 별도 계층에 둔다.
- 페이지는 얇게 유지하고, 실제 화면 조합은 `widgets`, 비즈니스 로직은 `features`, 핵심 모델은 `entities`로 분리한다.
- 다국어 처리를 고려해 화면 문자열은 i18n 리소스로 분리하고, 언어 상태와 초기화는 공통 계층에서 관리한다.
- Electron preload/IPC 중심 사고방식에서 벗어나 Tauri 플러그인 중심 구조로 바꾼다.
- 중복되는 UI와 로직은 이전 과정에서 공통 컴포넌트와 공통 유틸로 정리한다.

### 3.3 작업 원칙

- 레거시 `src/`에 개선할 점이 보이면 먼저 검토하고 반영 여부를 정한 뒤 `migration/`에 옮긴다.
- 한 번에 전체를 바꾸지 않고, 기능 단위로 이전하고 검증한다.
- 항상 실행 가능한 상태를 유지한다.

## 6. 목표 아키텍처

### 6.1 디렉터리 방향

```text
migration/src/
├─ app/                # 앱 조립, provider, layout, 글로벌 초기화
├─ pages/              # 라우트 진입점, 얇은 페이지 구성
├─ widgets/            # 여러 feature/entity를 조합한 화면 단위 블록
├─ features/           # 사용자 액션 중심 기능 단위
├─ entities/           # 핵심 도메인 모델, store, 타입, 비즈니스 규칙
├─ shared/             # 공통 UI, 유틸, API, 설정, 타입
└─ main.tsx            # 앱 진입점
```

### 6.2 구조 원칙

- `pages`: 라우트 진입점만 담당
- `widgets`: 페이지를 구성하는 주요 화면 블록 담당
- `features`: 로그인, 회원가입, 보정, 알림 설정 등 사용자 액션 중심 기능 담당
- `entities`: 사용자, 세션, 자세, 대시보드 등 핵심 모델 담당
- `shared`: 재사용 가능한 UI, API 클라이언트, 설정, 타입, i18n 초기화 담당

### 6.3 Tauri 쪽 구조 방향

```text
migration/src-tauri/
├─ src/
│  └─ lib.rs           # Tauri 부트스트랩, 플러그인 등록, 앱 초기화
├─ capabilities/       # 권한 설정
└─ tauri.conf.json     # 앱/윈도우/번들/플러그인 설정
```

## 9. 우선순위

현재 기준 추천 우선순위는 아래와 같다.

1. 인증 UI + 인증 공통 컴포넌트
2. 인증 API + 토큰 처리
3. 공통 UI 라이브러리 정리
4. 온보딩/보정 화면
5. 메인 대시보드 UI
6. 자세 측정 파이프라인
7. 위젯 윈도우 제어
8. 알림/자동 실행/업데이트 등 시스템 기능

이 순서는 다음 이유로 적합하다.

- 라우팅 이후 가장 빠르게 사용자 흐름이 살아나는 영역이 인증이다.
- 인증 UI를 옮기면 공통 UI 컴포넌트를 함께 정리할 수 있다.
- 메인/온보딩/위젯은 인증 기반이 정리된 뒤 이전하는 편이 안전하다.
- 자세 측정 파이프라인은 가장 복잡하고 검증 비용이 크므로 후반에 두는 것이 좋다.

## 11. 리스크와 대응

### 11.1 자세 측정 성능 리스크

설명:

- MediaPipe, webcam, 실시간 렌더링 성능이 Electron과 Tauri에서 다르게 나타날 수 있다.

대응:

- 측정 로직과 화면 렌더링을 분리한다.
- 성능 검증을 별도 단계로 둔다.

### 11.2 멀티 윈도우 리스크

설명:

- 위젯 창과 메인 창 간 상태 동기화가 Electron과 동일하게 동작하지 않을 수 있다.

대응:

- 상태 동기화 경계를 명확히 한다.
- 윈도우 기능을 전용 추상화 계층으로 감싼다.

### 11.3 플랫폼 기능 치환 리스크

설명:

- preload/IPC 방식이 사라지므로 초기 구조 혼선이 생길 수 있다.

대응:

- 기능별로 Electron API와 Tauri API 매핑표를 유지한다.
- 데스크톱 기능은 `shared/lib/desktop` 또는 기능별 adapter 계층으로 분리한다.

### 11.4 스타일 변경 리스크

설명:

- 구조 개선 과정에서 UI가 의도치 않게 바뀔 가능성이 있다.

대응:

- 구조만 바꾸고 스타일 클래스와 토큰은 보존한다.
- 페이지별 시각 비교를 수동 검증에 포함한다.
